Le point important est que le LLM n'est pas l'architecture.

Le LLM est un composant de l'architecture.

Le véritable produit est :

Intent Engine + Procedure Engine + Journey Engine + Evidence Engine.

3. Modèles NVIDIA
Il faut distinguer le modèle principal et les modèles spécialisés.

NVIDIA Build propose actuellement notamment glm-5-3-flash, un modèle multimodal avec raisonnement, compréhension image/texte et tool use, ainsi que muse-glimmer-30b, également multimodal avec raisonnement et tool calling. (NVIDIA NIM APIs)

Pour le prototype, je partirais sur :

Modèle principal
GLM-5.3-Flash

Rôle :

Intent
Reasoning
Structured output
Conversation
Image understanding si nécessaire
Il a l'avantage d'être multimodal et orienté raisonnement/tool use. (NVIDIA NIM APIs)

Document / OCR
Pour un traitement documentaire spécialisé, NVIDIA propose nemotron-parse-2.0, orienté extraction de texte et métadonnées depuis des images, ainsi que llama-nemotron-embed-vl-1b-v2 et llama-nemotron-rerank-vl-1b-v2 pour le retrieval multimodal. (NVIDIA NIM APIs)

Mais ne les intégrez que si le temps le permet.

Pour la démo principale :

GLM-5.3-Flash
        ↓
analyse texte
        +
analyse image
peut suffire.

Voice
NVIDIA référence également canary-1b-asr, destiné à la reconnaissance vocale multilingue et à la traduction automatique de la parole. (NVIDIA NIM APIs)

Mais là encore :

Voice = P1, pas P0.

20. Règles du Journey Engine
Exemple :

function calculateJourney(journey: Journey) {

  const required = journey.requirements
    .filter(r => r.required);

  const completed = required.filter(requirement => {

    const document = journey.documents
      .find(d => d.requirementId === requirement.id);

    return document?.status === "ANALYZED";
  });

  const completion =
    Math.round(
      (completed.length / required.length) * 100
    );

  return {
    completion,
    nextAction: resolveNextAction(journey)
  };
}

if (needsClarification)

Pour un seul parcours :

Official source
       ↓

       ↓
chunks
       ↓

       ↓

       ↓

Mais pour la première version, une approche encore plus robuste est :

Procedure JSON
+
Source JSON
+
Evidence
Puis utiliser le RAG uniquement pour les informations narratives.

23. Pourquoi ?
Parce que :

LLM → RAG → réponse
peut halluciner.

Alors que :

Procedure DB
       ↓
Rule Engine
       ↓
Journey
est beaucoup plus contrôlable.

Le RAG devient donc :

un outil de recherche de preuve, pas le moteur métier.

31. API /api/journey
export async function POST(req: Request) {

  const body = await req.json();

  const procedure =
    await resolveProcedure(body.intent);

  const journey =
    createJourney({
      procedure,
      userContext: body.userContext
    });

  return Response.json(journey);
}

55. Architecture finale simplifiée
Si vous devez l'expliquer au jury en 20 secondes :

« L'utilisateur parle naturellement à Sama Agent. Un modèle NVIDIA comprend son intention. Notre moteur sélectionne ensuite une procédure structurée, maintient l'état de son parcours et détermine ce qu'il lui manque. Les modèles multimodaux peuvent analyser les documents fournis, tandis que chaque exigence importante est reliée à une source. L'IA comprend et orchestre, mais les règles métier déterminent l'état du dossier. »

C'est la formulation technique à retenir.

Tout cela dilue le produit.

Le prototype gagnant doit rester :

UNE PERSONNE
      ↓
UNE DEMANDE
      ↓
UNE PROCÉDURE
      ↓
UN DOSSIER
      ↓
UNE PREUVE
      ↓
UNE PROCHAINE ACTION
C'est la colonne vertébrale de Sama Agent.

57. Le produit en une phrase
Sama Agent comprend ce que le citoyen veut faire, construit son parcours, regarde ce qu'il possède déjà, identifie ce qui lui manque et lui indique, preuves à l'appui, ce qu'il doit faire ensuite.

C'est cette phrase qui doit guider chaque ligne de code et chaque écran.
